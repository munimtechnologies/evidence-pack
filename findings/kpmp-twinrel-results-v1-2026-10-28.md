## What went wrong

- The job's offline tests passed (15 of 15).
- It ran on a different machine from the one that holds the cached KPMP files. The compute pool keeps one data volume per machine, which is why every KPMP job now starts with `kidney.kpmp_fill`.
- `kpmp_fill` reads only the small members of each package (feature workbooks, OME-XML, README) through HTTP range requests. **atlas.kpmp.org answered every range request with HTTP 200 instead of 206**, which means it ignores the `Range` header and would send the whole file. As designed, the fill gave up after 5 such answers (5 tried, 356 not attempted, 0 bytes read). It downloaded the small descriptor-score and clinical files whole.

The second point is a small, practical fact about the open data. Anyone who wants KPMP's pathomics workbooks without the slides inside the same zip must still download each package whole. The first five packages in our file list are 67.7 MB to 553 MB.

## What happens next

`kpmp-twinrel-v2` is the same study with the same code, data, seed and thresholds. Two steps change, and neither touches the analysis:

1. `kidney.kpmp_subset` (new, with a test) writes a v2-only copy of the file list. The study reads v2 packages only.
2. `kidney.kpmp_fill --allow-full` then downloads each v2 package whole, keeps the small members and deletes the zip. On the machine that already holds the cache, nothing is downloaded.

Its modules are taken unchanged from tag v0.9.20 of this repository. The predictions above are not changed.
